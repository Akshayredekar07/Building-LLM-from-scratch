10 — Input-Target Pair Generation

Input-Target Pair Generation

Before training an LLM, we need to create input-target pairs — each pair teaches the model to predict the next word given a context window. This is the fundamental self-supervised learning setup for all autoregressive language models.

Last Step Before Data Sampling

The previous step (tokenization) gave us a flat sequence of token IDs. The data preparation pipeline adds one final step: creating input-target pairs. These are passed to the model during training.

What do Input-Target Pairs look like?

Given a sequence of tokens, we slide a window of size context_size across the token stream. For each window position, the input is the window and the target is the same window shifted by one position to the right.

Example corpus: "The old city stood, the old library, a relic from the bygone era"

Key insight: Each step, we predict ONE word. The input grows by one token each step, until it fills the context window. Then the window slides.
LLM Prediction Flow

LLMs cannot directly access words as text — they work on subsamples of text which are blocks of tokens. During training time the model predicts one token at a time from these blocks.

Given a text sample

Pass the sample blocks as input to LLM. These LLMs are trained to predict the next word (token).

During training

We mask out all words, training one word at a time. After each prediction the context grows by one token.

These LLMs are trained

To predict the next token (word) given a context. The model learns word-order relationships from millions of these pairs.

Tensor Construction: x and y

The input pair is represented as two tensors: x containing input tokens and y containing target tokens. Both have the same shape — y is just x shifted by one position.

Python — Tensor Construction
import torch

# enc_sample: full list of token IDs
# Example: "The city, the old library" → tokenised
enc_sample = [2, 3, 4, 1, 5]  # token ID sequence
context_size = 4

# x: input tokens (first context_size tokens)
x = torch.tensor(enc_sample[: context_size])
# y: target tokens (shifted right by 1)
y = torch.tensor(enc_sample[1 : context_size + 1])

print("x (input):",  x)   # tensor([2, 3, 4, 1])
print("y (target):", y)   # tensor([3, 4, 1, 5])

# Every consecutive pair (x[i], y[i]) is one training example
for i in range(len(x)):
    print(f"input: {x[:i+1].tolist()} → target: {y[i].item()}")
One of the most intuitive ways to create a next word prediction dataset is by generating sequences of word predictions. The input context grows by one token each step — but the target is always just one word: the word at the next position.
11 — Sliding Window DataLoader

Sliding Window DataLoader

To feed input-target pairs into a model efficiently, we implement a custom PyTorch Dataset + DataLoader using a sliding window approach. The window moves one position at a time across the full tokenised corpus.

Sliding Window Concept

Instead of splitting the corpus into non-overlapping chunks, we slide a window of context_size tokens across the token stream. At each position, we extract one (x, y) pair. This maximises the number of training examples.

DataLoader Implementation

The DataLoader encapsulates four steps: tokenise the full text, use a sliding window to chunk input/target, return tensors, and batch them.

Python — GPT Dataset + DataLoader
import torch
from torch.utils.data import Dataset, DataLoader
import tiktoken
from tqdm import tqdm

# Sliding window dataset — generates overlapping (x, y) pairs
class GPTDatasetV1(Dataset):
    def __init__(self, txt, tokenizer, max_length, stride):
        # S1: tokenise entire text into a flat ID sequence
        token_ids = tokenizer.encode(txt, allowed_special={"<|endoftext|>"})

        self.input_ids  = []
        self.target_ids = []

        # S2: slide a window of max_length across the token stream
        # stride controls how many tokens we advance each step
        for i in range(0, len(token_ids) - max_length, stride):
            input_chunk  = token_ids[i : i + max_length]
            target_chunk = token_ids[i + 1 : i + max_length + 1]
            self.input_ids.append(torch.tensor(input_chunk))
            self.target_ids.append(torch.tensor(target_chunk))

    # S3: total number of (x, y) pairs
    def __len__(self):
        return len(self.input_ids)

    # S4: return one (x, y) pair by index
    def __getitem__(self, idx):
        return self.input_ids[idx], self.target_ids[idx]


def create_dataloader_v1(txt, batch_size=4, max_length=256,
                           stride=128, shuffle=True, drop_last=True):
    tokenizer = tiktoken.get_encoding("gpt2")
    dataset   = GPTDatasetV1(txt, tokenizer, max_length, stride)
    dataloader = DataLoader(
        dataset,
        batch_size=batch_size,
        shuffle=shuffle,
        drop_last=drop_last  # drop incomplete last batch
    )
    return dataloader

# Usage
with open("the-verdict.txt", "r") as f:
    raw_text = f.read()

dataloader = create_dataloader_v1(raw_text, batch_size=8,
                                    max_length=4, stride=4)

# Inspect first batch
data_iter = iter(dataloader)
inputs, targets = next(data_iter)
print("inputs shape :", inputs.shape)   # [8, 4]
print("targets shape:", targets.shape)  # [8, 4]
How the DataLoader Works Internally
Inputs are collected in a tensor

Inputs are collected in a tensor where each row corresponds to one input text (context). Rows are collected in a tensor where each row = one context window.

Sliding Window

The sliding window moves one step at a time. The stride parameter controls the overlap: stride=1 creates maximum overlap; stride=max_length creates non-overlapping windows.

Targets created by shifting

Send tensor containing the corresponding prediction targets, created by shifting the input by one position. These targets are created by shifting the window one token ahead.

Preprocessing note

It should return the input and target pairs. To implement an effective data loader — these tensors can be slices of multidimensional array. Inputs are collected in a tensor (where each row = one text). DataLoader depends on input context — each row represents the same token, and inputs are collected in a tensor where each row represents the tokens for prediction.

12 — Token Embedding

Token Embedding for Building a Language Model

After tokenisation we have integer token IDs. But neural networks require continuous numerical inputs. Token embedding converts each discrete integer ID into a dense floating-point vector. This is a necessary foundation for building any language model.

Why do we need token embeddings?
Conceptual Understanding

Small models use dense data. Playing with tokens embedding gives us a dense numeric representation of every token — this is the input that the actual neural network layers process.

What are token embeddings created for an LM?

We generate pairs — the embedding is created for an LM. At one line, token IDs are constructed at one time and then decoded (masked) to generate them.

Dense Representation

One-hot encoding (OHE) assigns sequential numbers — but this is too sparse and does not capture relationships. Embeddings are learned dense vectors that group semantically similar tokens together.

Why NOT One-Hot Encoding (OHE)?
OHE vs Dense Embeddings

OHE PROBLEMS

Issue 1: Increases dimensionality and assigns sequential numbers — not informative.
Issue 2: Fails to capture semantic meaning and sparse data relationships.
Issue 3: However the number fails to capture the relationship between tokens. For example "cat" OHE = (0,1,0,0,...) and "kitten" OHE = (0,0,1,0,...) — the numbers don't show they are similar.

DENSE EMBEDDINGS

We can train a neural network (NN/neural network) that gives each token a similar output as like encoding — vector embeddings. Which give each token similar vector of a character/encoding representation.

Semantic Meaning Similarity: Semantically similar words should have similar embedding vectors. The embedding layer is trained alongside the model so that similar-context tokens cluster in vector space.

13 — Vocabulary Embedding with NN

Token embeddings are built using a weight matrix called the Embedding Matrix. This matrix maps each token ID to a unique dense vector. The entire vocabulary gets one row each in this matrix. The matrix is learned during training.

Python — Token Embedding with PyTorch
import torch
import torch.nn as nn

vocab_size   = 50257  # GPT-2 vocabulary size
embed_dim    = 768    # embedding dimension (hidden size)

# Embedding layer: lookup table of shape (vocab_size, embed_dim)
# Each row is the embedding vector for one token ID
token_embedding_layer = nn.Embedding(vocab_size, embed_dim)

# Example: batch of token IDs from DataLoader
# inputs shape: (batch_size, context_length) = (8, 4)
inputs = torch.tensor([
    [9, 8, 1, 20, 21],   # first text in batch
    [1, 3, 4, 5, 7],    # second text in batch
])  # shape: (2, 5)

# For each token ID, fetch the corresponding row in the embedding matrix
token_embeddings = token_embedding_layer(inputs)

print("inputs shape        :", inputs.shape)            # (2, 5)
print("token_embeddings    :", token_embeddings.shape)   # (2, 5, 768)

# Dry run for one token:
# token_id = 9 → embedding_layer.weight[9] = a 768-dim vector
# embedding_layer.weight shape = (50257, 768)

idx = 9
single_vec = token_embedding_layer.weight[idx]
print("single token vector shape:", single_vec.shape)  # (768,)
Key insight: nn.Embedding(vocab_size, embed_dim) is nothing but a weight matrix of shape (vocab_size, embed_dim). Looking up token ID k simply fetches row k from this matrix. The entire operation is O(1) — a simple index lookup, not a matrix multiplication.
14 — Embedding Layer Details

What Does the Embedding Layer Actually Do?

The embedding layer is a lookup table operation — not a matrix multiplication. It takes an integer token ID and retrieves the corresponding row from the embedding weight matrix. Understanding the exact shapes and operations is critical for debugging and building LLMs from scratch.

The Embedding Layer is a Lookup Table

The embedding layer is a lookup table operation that retrieves rows from the embedding matrix using the input token IDs as indices.

Lookup Mechanics
$$\text{Given: } \text{input\_ids} = [k_1, k_2, \ldots, k_n] \quad \text{(token IDs)}$$ $$W_E \in \mathbb{R}^{V \times d} \quad \text{(embedding weight matrix, V=vocab, d=dim)}$$ $$\text{Output: } \mathbf{E} = W_E[\text{input\_ids}] \in \mathbb{R}^{n \times d}$$ $$\text{i.e., } \mathbf{E}[i] = W_E[k_i] \quad \text{(row lookup, not matmul)}$$
Performing lookup: embedding lookup — embedding matrix has a weight matrix layer that has weight. The embedding is not computed — it is fetched. The index is the token ID; the output is the row at that index.

This is architecturally similar to a neural network
One input note: This is architecturally similar to a neural network (NN). The input note ID is (0,1,0,0...) — one-hot vector. One input note is multiply with embedding matrix to give one 768-dim output (embedding vector).
But much more efficient: Embedding layers are much more computationally efficient than one-hot encoding + matrix multiplication. Instead of doing a full matmul, we just index into the matrix — O(1) per token.

Positional Encoding — Preview
Problem so far: Until now we looked at the embedding layer — the same token ID always gets the same embedding vector, regardless of its position in the sentence. In embedding, two identical tokens in different positions get identical representations. The order of words is lost entirely. This is a fundamental limitation — word order matters in language.

Example: "the cat sat on the mat"

Both occurrences of "the" (position 0 and position 4) get the exact same embedding vector from the lookup table. The model cannot distinguish which "the" is which. This is problematic — sentence meaning is order-dependent (translation, summarisation, Q&A all rely on word order).

Summarisation of issue: Basic embedding layers lack positional information. The same token ID is mapped to the same vector representation regardless of where the token is positioned in the input sentence.
15 — Positional Encoding

Positional Encoding

Positional encoding injects information about where each token appears in the sequence into the model. Without it, Transformers are order-invariant — they treat input as a set, not a sequence. Positional encoding makes the model sequence-aware.

Why Positional Information is Needed
The Core Problem

Token embedding does not capture positional information. Words like "the cat sat" vs "sat the cat" would have identical representations — but mean different things.

To resolve this

It is helpful to inject the additional positional information into the model by adding positional encoding into the model's embedding for each word containing the same vector.

Solution

Encode order information: each position in the sequence should add or modify the token embedding to encode where it is. Positional encoding adds a unique signature to each position.

Two Types of Positional Encoding
① Absolute Positional Encoding: For each position in the input sequence, a unique embedding is added to the token's embedding. For each position in the input sequence, a unique embedding is assigned to the token's embedding, regardless of whether the same word appears at different positions.
② Relative Positional Encoding: It focuses on the relative position and distance between tokens instead of their exact location in the sequence. The model learns the relationship in terms of distance between tokens, not their absolute position index.
It is helpful for injecting output

Positional information is helpful for injecting the LLM output. The model processes all tokens in parallel during training (unlike RNNs), so positional encoding is the only way the model knows the order of tokens.

16 — Absolute Positional Encoding

Absolute Positional Embedding

Absolute PE assigns a unique vector to each absolute position index (0, 1, 2, …). For each position in the input sequence, a unique embedding is added to the token's embedding. GPT-2 and GPT-3 use learned absolute positional embeddings.

Mathematical Definition
$$\mathbf{h}_t = \mathbf{e}_t + \mathbf{p}_t$$
$$\text{where} \quad \mathbf{e}_t = W_E[\text{token\_id}_t] \in \mathbb{R}^d \quad \text{(token embedding)}$$ $$\mathbf{p}_t = W_P[t] \in \mathbb{R}^d \quad \text{(positional embedding, } t = \text{position index)}$$ $$W_P \in \mathbb{R}^{T_{\max} \times d} \quad \text{(positional embedding matrix, learned)}$$

The final input to the Transformer is the element-wise sum of the token embedding and the positional embedding. Both are the same dimension d.

Python — Absolute Positional Embedding (GPT-2 style)
import torch
import torch.nn as nn

vocab_size    = 50257
context_len   = 1024   # max sequence length GPT-2 supports
embed_dim     = 768

# Token embedding: maps token ID → dense vector
token_embedding_layer    = nn.Embedding(vocab_size, embed_dim)

# Positional embedding: maps position index → dense vector
# Shape: (context_len, embed_dim) = (1024, 768)
position_embedding_layer = nn.Embedding(context_len, embed_dim)

# Example inputs: batch of token ID tensors
# inputs shape: (batch_size, seq_len) = (8, 4)
inputs = torch.tensor([
    [9, 8, 16, 23],
    [1, 3, 4, 5],
])  # (2, 4)

# Token embeddings: (batch, seq_len, embed_dim)
tok_emb = token_embedding_layer(inputs)  # (2, 4, 768)

# Position indices: [0, 1, 2, 3] for seq_len=4
# arange gives positions; same positions for every batch item
pos_indices = torch.arange(inputs.shape[1])   # [0, 1, 2, 3]
pos_emb = position_embedding_layer(pos_indices)  # (4, 768)

# Add: broadcasting handles the batch dimension automatically
# tok_emb: (2, 4, 768) + pos_emb: (4, 768) → (2, 4, 768)
input_embeddings = tok_emb + pos_emb

print("tok_emb shape        :", tok_emb.shape)          # (2, 4, 768)
print("pos_emb shape        :", pos_emb.shape)          # (4, 768)
print("input_embeddings     :", input_embeddings.shape)  # (2, 4, 768)

# state  → inputs = [[9,8,16,23],[1,3,4,5]]

Sinusoidal Absolute PE (Original Transformer)
$$PE_{(pos, 2i)} = \sin\!\left(\frac{pos}{10000^{2i/d}}\right)$$ $$PE_{(pos, 2i+1)} = \cos\!\left(\frac{pos}{10000^{2i/d}}\right)$$ $$\text{where } pos = \text{position index}, \; i = \text{dimension index}, \; d = \text{embedding dim}$$
GPT-2 uses learned PE (not sinusoidal). W_P is trainable and optimised jointly with the rest of the model weights. Sinusoidal PE is fixed (not learned) and has the useful property that relative positions can be recovered as linear combinations of the PE vectors.
17 — Relative Positional Encoding

Relative Positional Embedding

Relative PE focuses on the distance between tokens rather than their absolute position index. This lets the model generalise to sequences longer than those seen during training.

Mathematical Definition
$$\text{Absolute PE: } \mathbf{h}_t = \mathbf{e}_t + \mathbf{p}_t$$ $$\text{Relative PE (Shaw et al.): } a_{ij} = \text{softmax}\!\left(\frac{\mathbf{q}_i^\top (\mathbf{k}_j + \mathbf{e}_{i-j})}{\sqrt{d_k}}\right)$$ $$\text{where } \mathbf{e}_{i-j} = W_P[i-j] \quad \text{(learnable vector for relative distance)}$$

Absolute PE is suitable for fixed order of tokens — autoregressive sequence generation. OpenAI GPT models use absolute positional embeddings optimised during training.
Relative PE is suitable for tasks like language modelling over long sequences where the same phrase can appear in different parts of the text.
Python — ALiBi Relative PE Bias
import torch

# ALiBi: add linear bias to attention scores based on token distance
# bias[head][i][j] = -slope[head] * |i - j|
def get_alibi_bias(seq_len, num_heads, device='cpu'):
    slopes = torch.tensor([
        2 ** (-8 / num_heads * i)
        for i in range(1, num_heads + 1)
    ], device=device)   # shape: (num_heads,)

    positions = torch.arange(seq_len, device=device)
    rel_dist  = (positions.unsqueeze(0) - positions.unsqueeze(1)).abs()
    bias = -slopes[:, None, None] * rel_dist.unsqueeze(0)
    return bias   # (num_heads, seq_len, seq_len)

# In attention: attn_scores = Q @ K.T / sqrt(d_k) + alibi_bias
bias = get_alibi_bias(4, 8)
print("ALiBi bias shape:", bias.shape)  # (8, 4, 4)

# Dry run (head=0, slope≈0.707, seq_len=4):

Python — Complete GPT-2 Embedding Module
import torch
import torch.nn as nn

class GPT2Config:
    vocab_size  = 50257
    context_len = 1024
    embed_dim   = 768
    drop_rate   = 0.1

class GPT2EmbeddingLayer(nn.Module):
    # Token embedding + Positional embedding — both learned
    def __init__(self, cfg):
        super().__init__()
        self.token_emb    = nn.Embedding(cfg.vocab_size, cfg.embed_dim)
        self.position_emb = nn.Embedding(cfg.context_len, cfg.embed_dim)
        self.drop         = nn.Dropout(cfg.drop_rate)

    def forward(self, token_ids):
        B, T = token_ids.shape
        tok_emb = self.token_emb(token_ids)              # (B, T, d)
        pos_ids = torch.arange(T, device=token_ids.device)
        pos_emb = self.position_emb(pos_ids)             # (T, d)
        return self.drop(tok_emb + pos_emb)            # (B, T, d)

cfg = GPT2Config()
emb = GPT2EmbeddingLayer(cfg)

token_ids = torch.randint(0, cfg.vocab_size, (2, 4))
out = emb(token_ids)
print("output shape:", out.shape)  # (2, 4, 768)

# action → tok_emb + pos_emb → (2,4,768)  [broadcast over batch]
